Engineering · System Design

Mappealo Platform Architecture

From prototype to platform
Target: 600+ layers · public scale
v1 — for technical review

Direct answer: no, not yet — and that was the right call until now

What exists today is an MVP built to prove the concept, and it does that: retrieval grounded strictly in La Maraña's documents, a working map, bilingual answers, citations. That was the correct thing to build first.

It will not scale to 600 layers or public traffic. Two of the failures are already measurable in the current 10-layer build — including one that is a correctness problem, not a performance one. The retrieval side, by contrast, was built on foundations that do scale.

This document states what breaks, what holds, and the architecture to move to — sequenced so the product keeps working throughout.

01Current state — measured, not estimated

Every number below was taken from the running system today.

Hazard layers are silently truncated Critical · correctness

The layer endpoint caps output at _MAX_FEATURES = 6000. The landslide susceptibility layer holds 53,935 features, so 89% of it never reaches the user — with no warning in the UI or the payload. A resident can look at the landslide layer, not see their hillside highlighted, and conclude they are safe. For a hazard tool this is the most serious defect in the system.

layer_landsl_monroe_plus_slop50pct → 53,935 in DB · 6,000 served · 1.3 MB

Whole layers ship to the browser as GeoJSON Critical · scale

Each layer is serialized in full and sent over HTTP. One land-use layer is 26.4 MB for fewer than a thousand features, because the polygons are detailed. At 600 layers this is not slow — it is impossible, and on the mobile connections most community users have, even two or three layers is already unusable.

layer_plan_uso_terrenos_2015 → 996 features · 26.4 MB single response
10 layers today = 63,628 features · projected 600 layers

Layer metadata is hardcoded in JavaScript Blocker at scale

Display names, categories and translations live in a literal dictionary in the frontend (LAYER_LABELS, CATEGORY). Adding a layer means editing and redeploying the client. This is workable for 10 and absurd for 600 — and it is the root reason the layer panel looks thin: there is no data model behind it to design against.

Layer cache is per-instance and unbounded Warning

Built GeoJSON is held in a process-local dictionary. It is not shared between Cloud Run instances, is lost on every deploy, and has no eviction — memory grows until the instance is recycled. With 600 layers a single instance cannot hold the working set.

The embedding model runs inside the API process Warning

Every question loads and runs a sentence-transformer in the request path. It inflates cold starts, ties CPU-heavy inference to request-serving capacity, and means the API cannot scale on request volume independently of model load.

Retrieval foundations are sound Holds up

The parts that are hardest to retrofit were done correctly: an HNSW index on the embedding column (approximate-nearest-neighbour, not a sequential scan), GiST indexes on every spatial table, and a normalized document/chunk schema with provenance. Retrieval will scale from 45K to millions of chunks on this design.

idx_document_chunks_embedding · hnsw (embedding vector_cosine_ops)
GiST indexes on layer tables: 10 / 10 · chunks today: 45,596

No authentication, authorization, rate limiting or quotas Blocks public launch

Every endpoint is open and unmetered. A single script could exhaust the Vertex AI budget in minutes. There is no notion of identity, role, tenant, or per-caller limit anywhere in the system.

03The decisions that matter

3.1  Vector tiles replace GeoJSON

The single highest-value change. It fixes the truncation bug and the payload problem at the same time.

DimensionToday · GeoJSONTarget · Vector tiles (MVT)
Unit of transferEntire layerOne 512px tile at the viewed zoom
Land-use layer26.4 MB~20–60 KB per tile
Landslide layerTruncated to 6,000 of 53,935Complete — generalized per zoom, never dropped
CachingPer-instance memoryImmutable URLs, cached at CDN edge
600 layersNot possibleCost scales with what is viewed, not what exists
 
-- PostGIS generates the tile directly; no application-side geometry work.
SELECT ST_AsMVT(t, 'layer', 4096, 'geom') FROM (
  SELECT id, name,
         ST_AsMVTGeom(geom, ST_TileEnvelope(:z, :x, :y), 4096, 64, true) AS geom
  FROM layer_landslide
  WHERE geom && ST_TileEnvelope(:z, :x, :y)   -- GiST index does the work
) t;

Generalization is per zoom level, so a statewide view sends simplified geometry and a street-level view sends full detail — the user always sees the whole layer, at the fidelity the view warrants. Tiles are immutable and versioned by dataset, so the CDN can hold them indefinitely.

3.2  A layer registry, not a JavaScript dictionary

600 layers need a data model with facets, translations and provenance — which is also what makes a serious layer browser designable.

CREATE TABLE layer_registry (
  id              text PRIMARY KEY,
  name_es         text NOT NULL,   name_en  text NOT NULL,
  category        text NOT NULL,   subcategory text,
  keywords        text[],                    -- drives search + chat layer matching
  source_agency   text NOT NULL,   source_inventory text NOT NULL,  -- provenance, always
  vintage_year    int,                       license text,
  geometry_type   text,                      feature_count bigint,
  min_zoom        int DEFAULT 0,      max_zoom int DEFAULT 14,
  style           jsonb,                     -- colour, opacity, legend — server-driven
  dataset_version text NOT NULL,   -- cache-busts tiles on refresh
  status          text DEFAULT 'published'
);

What this unlocks in the product

  • Server-side search and facets — filter by agency, hazard type, vintage, geography.
  • Adding a layer is a data operation, not a frontend deploy.
  • Provenance on every layer — the promise made to La Maraña, enforced in the schema.
  • Server-driven styling — legend and colour defined once, consistent everywhere.

What the layer browser becomes

  • Search-first, because nobody scrolls 600 rows.
  • Faceted filters and a virtualized list.
  • Curated layer sets — "Flood planning", "Facility siting" — as one-click presets.
  • Recently used and saved per user, once identity exists.

3.4  Authentication, authorization and quotas

Designed now, enforced from the first public deployment.

RoleIdentityCan doLimits
AnonymousNonePublic layers, ask questions, view citationsTight per-IP quota, CAPTCHA on burst
Community memberEmail / OIDCSaved areas, history, feedback on answersStandard daily quota
PlannerOIDC + orgDraft layers, exports, comparison toolsElevated quota
Partner / APIAPI keyProgrammatic query + tile accessContracted rate, metered
AdminOIDC + rolePublish layers, manage registry, view evalsAudited

Authorization is enforced at the gateway and again in the data layer via row-level security on status and tenant, so an unpublished layer cannot leak through a tile request even if a URL is guessed. Every LLM call is metered per caller, which is what makes the Vertex AI spend predictable rather than unbounded.

04Sequencing

Ordered by risk retired per unit of work. The product stays usable throughout; nothing here requires a rewrite.

P0

Stop shipping wrong data

Days
  • Surface the truncation immediately — until tiles land, the API must report when a layer is capped and the UI must say so. A silent 89% gap in a hazard layer cannot stand another week.
  • Cap payload responsibly — return an explicit error rather than a quietly partial layer.
Retires the one defect that could mislead a resident about their own risk.
P1

Vector tiles + layer registry

3–4 weeks
  • Tile endpoint backed by ST_AsMVT; migrate the existing 10 layers.
  • layer_registry table, seeded from the current catalog plus La Maraña's data dictionaries.
  • Catalog API with search, facets and pagination; delete the hardcoded frontend dictionaries.
  • CDN in front of tiles; shared Redis cache replaces the in-process dictionary.
Unlocks 600 layers, fixes truncation properly, and makes the layer browser designable.
P2

Identity, quotas and the public edge

2–3 weeks
  • Gateway with global rate limiting and WAF; OIDC login and API keys.
  • Role model above, enforced at gateway and by row-level security.
  • Per-caller metering on LLM spend, with budget alerts.
Makes a public launch safe — and resolves the open NYU access question either way.
P3

Retrieval quality and throughput

3–4 weeks
  • Embedding inference moved out of the request path into its own autoscaled service.
  • Hybrid search and cross-encoder reranking.
  • Semantic answer cache and streamed responses.
  • Eval harness wired into CI as a merge gate, extending the retrieval eval already in the repo.
Answer quality becomes a measured, defended property rather than an impression.
P4

Platform operations

Ongoing
  • Orchestrated, versioned ingestion with dataset lineage and rollback.
  • Tracing and per-query cost and latency attribution.
  • Read replicas; tile pre-rendering for the heaviest layers.
  • Feedback loop from reported answers back into evaluation sets.
Makes the system operable by La Maraña after handoff, not just by us.

05What this means

Cost

  • Tiles lower cost — CDN-cached bytes are far cheaper than repeated database reads and egress.
  • Redis and CDN add a modest fixed monthly floor.
  • Semantic caching cuts the LLM line, typically the largest variable cost at public volume.
  • Metering makes spend bounded — today a single script could drain the Vertex budget.

Consequences if deferred

  • The truncation defect persists — the tool understates hazard exposure with no warning.
  • Layers stall around 20–30, far short of 600, on payload alone.
  • Every new layer needs a frontend deploy — La Maraña could never self-serve after handoff.
  • Public launch stays unsafe without quotas, regardless of the NYU access decision.

None of this is a rewrite. The database schema, the grounding design, the spatial model and the retrieval index all carry forward unchanged — they were built correctly. What changes is how geometry reaches the browser, where layer metadata lives, and the operational layer around the system that an MVP legitimately did without.
