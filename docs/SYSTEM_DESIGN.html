Mappealo answers questions about land, hazard and planning in Puerto Rico using only documents and geospatial layers La Maraña provides. Two halves — a map you can interrogate and an assistant that can only speak from the loaded data — and the design problem is keeping both honest as the catalog goes from ten layers to six hundred.

The one rule the whole system serves

Every statement the product makes is traceable to something La Maraña supplied. The assistant is forbidden outside knowledge and emits no links of its own; every layer carries the agency, year and inventory it came from, plus how confident that metadata is — using La Maraña's own vocabulary: confirmed, inferred, reconstructed, unknown. Asked for the capital of France, it declines and shows no sources.

What the tile work actually bought

The source geometry is the bottleneck, not the pipeline. Plan de Uso holds 29.3 million vertices across 996 polygons; one landslide polygon alone has 567,502. Generalising that on every request is what made the map crawl, so it is now done once at ingest into two pyramid levels.

At zoom 12 — where people actually work — land use went from 190 KB / 1.67 s to 21 KB / 0.28 s, and landslide from 4.06 s to 0.47 s. Island-wide views are still ~3 s for the two heavy layers, cached after the first build.

Three failures worth remembering, because they recur at 600

Silent truncation. The old endpoint capped output at 6,000 features, so the landslide layer showed 11% of itself with no warning — a hazard map that understates hazard. Tiles removed the cap.

Silent empty tiles. Then a slow tile timed out, my code returned an empty tile, and half of Puerto Rico rendered as land with no land-use classification. Same mistake in a new place: missing data that looks like real data. Failures now return 503 and stay visible.

Orphaned queries. Killing the server does not cancel a running query — Postgres keeps going. Three tile queries ran for 36 minutes, pinning a 1-vCPU instance. Timeouts are now set on the connection, not per call, because on Cloud Run instances are recycled constantly and these accumulate.

03What has to change for 600

Tiles get baked, not generated

Generating a tile per request works at ten layers on one small instance. It will not hold at six hundred: the expensive tiles are the zoomed-out ones, every viewer wants them, and each costs seconds of database CPU. The standard answer is to build each layer's tile pyramid once and serve static files.

ApproachHowCost shapeFit here
Dynamic — todayST_AsMVT per requestDB CPU per viewfine at 10, ceiling at 600
Pre-baked PMTilesBuild once → one file on Cloud Storage → CDNnear-zero per viewrecommended
Managed — Mapbox, ESRIUpload; they host and servemetered per usera bill La Maraña inherits

Our 600 layers are reference data that rarely changes — close to the ideal case for baking. A rebuild runs only when La Maraña republishes a layer, and dataset_version in the registry already busts the cache when they do.

The spatial engine is the real missing half

The assistant can retrieve documents and read point-in-polygon facts. It cannot yet answer "schools within 500 m of a river in Arecibo", or "what percentage of this parcel is in a flood zone" — questions that need buffers, overlays and zonal statistics. That is a service, not a prompt change.

How a question becomes a spatial query matters as much as that it can. Letting a model emit SQL against the database is the fast path and the dangerous one. The design here is a constrained tool layer: a fixed set of parameterised spatial operations the model may call, never free-form SQL. Slower to build, auditable, and every number stays explainable and citable — which is the same standard the documents are held to.

Ingest has to condition geometry

Two of ten layers arrived pathological. At that rate, roughly a hundred and twenty of six hundred will be. Measuring vertex counts, simplifying into pyramid levels, and flagging the outliers belongs in the loader — discovering it at layer 400 is not a plan.

# what every incoming layer passes through
measure    → vertices, size, geometry validity, SRID
condition  → geom_simple (~30 m) and geom_coarse (~350 m), both indexed
register   → layer_registry row: names, category, provenance, confidence
verify     → tile a sample z/x/y at each pyramid level before publishing

Written to be resumable, because it has to be: the first version ran one UPDATE per layer and dropped the connection fifteen minutes into a 5.7-million-vertex layer. It now commits in batches and skips rows already done.

04The interface question

"I like the Mapbox interface" — what that actually means

Mapbox's look does not come from the Mapbox library. MapLibre is a fork of Mapbox GL JS — the same rendering engine. What reads as "Mapbox quality" is the basemap style: a vector basemap with restrained, desaturated cartography and careful label typography, so data layers sit on top instead of fighting the ground.

We are currently drawing on raw OpenStreetMap raster tiles, which are dense, saturated and designed to be read on their own. That is the entire difference.

What to change

  • A muted vector basemap. Protomaps ships an open basemap as a single PMTiles file we can host ourselves — no key, no per-view billing, and it matches the tile pipeline we are already building.
  • Restrained layer styling. Hazards read as texture and pattern, boundaries as hairlines, facilities as points. Not six flat fills competing.
  • One accent. Semantic colour reserved for hazard severity, never decoration.
  • Map-first layout. Panels float over the map rather than pushing it down.

Multiple layers at once

Today every polygon layer draws as a flat 35% fill, so two together are mud and three are unreadable. The fix is compositional rather than cosmetic:

  • One fill at a time. The most recently added polygon layer fills; earlier ones drop to outline.
  • Hazards as hatch. Patterns overlay legibly where flat fills cannot.
  • Order follows meaning. Boundaries beneath, hazards above, facilities on top — not add-order.
  • Legend earns its place once more than one layer is on.
